# Boulder Architecture & Component Guide

Boulder is a JDBC-level proxy framework designed to intercept database interactions, allowing for a "Virtual-First" architecture. It completely isolates the physical database from write operations (`INSERT`, `UPDATE`, `DELETE`) by trapping them in an in-memory state layer. For read operations (`SELECT`), it seamlessly merges the physical data with the in-memory state, providing a unified, coherent view to the application (e.g., Hibernate) as if the database was actually modified.

This guide details how each component of the Boulder framework contributes to this architecture.

## 1. `PitonDriver` (The Entry Point)
The `PitonDriver` is a custom JDBC driver.
*   **Purpose**: Acts as the initial interception layer. It registers itself with the `DriverManager`.
*   **Mechanism**: It listens for JDBC URLs that start with the prefix `jdbc:boulder:` (e.g., `jdbc:boulder:jdbc:h2:mem:cragdb`). When a connection is requested, it strips its prefix, uses the underlying real driver (e.g., H2) to establish a physical connection, and then wraps that physical `Connection` inside a `PitonConnection`.

## 2. `PitonConnection` (The Connection Wrapper)
Wraps the standard `java.sql.Connection`.
*   **Purpose**: Intercepts the creation of `Statement` and `PreparedStatement` objects.
*   **Mechanism**: 
    *   Any time the application requests a statement, it wraps the underlying physical statement in a `PitonStatement` or `PitonPreparedStatement`.
    *   It also contains logic to detect "Proxy Operations" (like `select next value for hibernate_sequence`). If detected, it entirely bypasses creating a physical prepared statement, knowing that the proxy will handle the ID generation in memory.

## 3. `PitonStatement` & `PitonPreparedStatement` (The Execution Interceptors)
Wraps the standard JDBC execution interfaces.
*   **Purpose**: To intercept execution methods (`executeQuery`, `executeUpdate`, `execute`, `executeBatch`) and redirect write operations to the in-memory state instead of the physical database.
*   **Mechanism (Writes)**: If it detects an `INSERT`, `UPDATE`, or `DELETE` query, it **does not** execute it on the delegate statement. Instead, it passes the SQL and parameters to the `DynoMerger`. It also handles intercepting requests for `getGeneratedKeys()` by providing a spoofed `GeneratedKeysResultSet`.
*   **Mechanism (Reads)**: For `SELECT` queries, it executes the query against the physical database, but wraps the resulting physical `ResultSet` inside a `MergedResultSet` before returning it to the application.
*   **Mechanism (Sequences)**: Intercepts ID generation queries (e.g., `call next value for`) and returns a new ID generated by the in-memory `ChalkBag`, bypassing the database sequence entirely.

## 4. `ChalkBag` (The In-Memory State Store)
The `ChalkBag` is the core memory layer that holds all uncommitted, virtual state.
*   **Purpose**: To store patches, inserts, and tombstones (deletes) in memory, isolated per thread.
*   **Mechanism**:
    *   Uses a `ThreadLocal` structure to ensure thread safety (typically binding to the lifecycle of an HTTP request or transaction).
    *   Data is stored as a nested map: `TableName -> PrimaryKey -> ColumnName -> Value`.
    *   **Tombstones**: If a row is deleted, its map value is set to `null`, acting as a "tombstone" to mask the physical row from read queries.
    *   **ID Generation**: Contains an `AtomicInteger` (starting at 1,000,000) to safely generate virtual primary keys that won't collide with existing physical IDs.

## 5. `DynoMerger` (The Write Engine)
The `DynoMerger` is the proxy's write mutation layer. It intercepts physical data modification statements and applies them exclusively to the `ChalkBag` memory state.

### Deep Technical Mechanics:
1.  **AST Parsing & Parameter Extraction**: 
    The engine relies on `JSqlParser` to convert raw SQL strings into an Abstract Syntax Tree (AST). It walks this AST to resolve tables and extract column mutation sets. For bound values, `getExpressionValue()` bridges the gap between raw AST nodes (like `LongValue`, `StringValue`) and parameterized queries (`JdbcParameter`), accurately pulling the correct index from the intercepted `PreparedStatement`'s internal parameter map.
2.  **`INSERT` Generation & Interception**:
    *   It extracts the specified columns and their respective values.
    *   If the exact Primary Key (typically determined via DatabaseMetaData, falling back to `id` or columns ending in `_id`) is not provided in the `INSERT` statement, `DynoMerger` uses `ChalkBag.get().generateId()` to assign a high-bound integer key (starting at 1,000,000) to avoid physical sequence conflicts.
    *   The values map is inserted directly into the `ChalkBag`. It returns a `WriteResult` object that encapsulates `affectedRows=1` and populates `generatedKeys` so the ORM can successfully map the newly minted virtual entity back to its context.
3.  **Targeted PK `UPDATE` & `DELETE`**:
    *   If the `WHERE` clause evaluates an exact match on the table's Primary Key (e.g., `WHERE employeeId = 101`), `DynoMerger` performs an immediate `O(1)` mutation in the `ChalkBag`—either overlaying a patch map for an `UPDATE` or inserting a `null` map tombstone for a `DELETE`.
4.  **Non-PK `UPDATE` & `DELETE` (The Resolution Phase)**:
    *   If a write operation relies on a non-PK condition (e.g., `DELETE FROM OrgUser WHERE organizationId = 100`), the proxy must discover *which specific rows* are affected to create precise patches.
    *   It calls `resolveAndApply()`, which dynamically generates and executes a physical query (`SELECT id FROM OrgUser WHERE organizationId = 100`) against the read-only underlying JDBC connection.
    *   It then iterates over both the physical results *and* the current virtual `ChalkBag` state, finding all matching primary keys. It finally applies the corresponding update/tombstone patches to every discovered key in memory. The actual `DELETE/UPDATE` statement is safely swallowed and never executed on the physical driver.

## 6. `MergedResultSet` (The Read Engine)
`MergedResultSet` is the most sophisticated component in Boulder. It wraps the physical database's `ResultSet` and seamlessly intertwines the real-world data with the virtual `ChalkBag` state, all while dynamically enforcing complex SQL constraints.

### Deep Technical Mechanics:
1.  **SQL Metamodel Mapping**:
    Upon instantiation, it parses the `SELECT` query to build critical mappings:
    *   **Alias Resolution**: Maps SQL aliases back to their canonical table names (removing quotes/backticks) using `LinkedHashMap` to respect the primary driving table order.
    *   **Join Topology (`resolveJoins`)**: Recursively walks `AndExpression` and `Parenthesis` nodes inside the `ON` clause to map `JoinInfo` (e.g., Table A's column linking to Table B's column).
    *   **Projection Mapping (`mapSelects`)**: Creates an index of which specific `table.column` corresponds to which physical `ResultSet` column index `i`.
    *   **Filter Extraction (`extractFilters`)**: Recursively maps the `WHERE` clause into an internal `whereFilters` dictionary, identifying exactly what criteria a row must meet to be yielded.
2.  **The Virtual Iteration (`loadVirtual()`)**:
    *   Before physical iteration begins, Boulder must prepare all purely virtual records (inserts that don't exist physically).
    *   It iterates through the `ChalkBag`. Since an in-memory row might only contain raw scalar data for a single table, but the query requires `JOIN` data, it calls `buildFullVirtualRow()`.
    *   `buildFullVirtualRow()` heavily leverages `resolvePkAcrossJoinRecursive()`. If a query joins `Employee` -> `Department` -> `Organization`, this recursive function traverses the defined `JoinInfo` map. It looks at the virtual `Employee`'s patched `dept_id`, uses it to find the matching `Department`, reads that department's `org_id`, and resolves the final `Organization`. It actively fetches missing attributes via localized physical `SELECT` queries to construct a mathematically complete "hybrid row".
    *   This hybrid row is evaluated against `matchesAllFilters()`. If it passes the `WHERE` clause, it is added to the `virtualRows` queue.
3.  **Physical Iteration (`while (delegate.next())`)**:
    *   The `MergedResultSet` delegates `.next()` to the physical DB.
    *   **Tombstone Check**: It checks the primary key against the `ChalkBag`. If marked as `null` (deleted), it instantly `continue`s, masking the row from the application.
    *   **Patch-to-Exclude Check (`checkFiltersSkip()`)**: If a physical row passed the DB's `WHERE` clause, the proxy verifies if any in-memory patches violate that clause. It extracts the physical values, applies any `ChalkBag` patches on top of them, and re-evaluates the resulting hybrid data against `whereFilters`. If the patched data now fails the filters, it skips the physical row.
    *   **Patch-to-Include**: Conversely, if a physical row originally failed the DB's `WHERE` clause, but a memory patch *makes* it pass, the `loadVirtual()` phase will have mathematically reconstructed that row and placed it in the `virtualRows` queue to be yielded after the physical loop exhausts.
4.  **Value Overrides (`getObject(i)`)**:
    When the ORM calls `rs.getString("username")`, `MergedResultSet` checks if the row's PK has an override mapped in the `ChalkBag` for the `username` column. If a patch exists, it returns the memory value; otherwise, it delegates to the physical `ResultSet`.
5.  **Aggregate Hijacking (`isAggregate`)**:
    If the query is identified as a scalar operation (e.g., `COUNT()`), `delegate.next()` only reads the physical scalar integer. Boulder hijacks this scalar, iterates through the `ChalkBag`, decrements the scalar for every matched tombstone, increments it for every newly matching virtual insert, and yields exactly one row containing the mathematically corrected sum.
6.  **In-Memory Sorting (`isSorted`) & Distinct (`isDistinct`)**:
    Because the physical database cannot sort rows that only exist in memory, the presence of an `ORDER BY` clause alters the proxy's behavior drastically. It pulls the *entire* physical dataset into an array, blends it with the `virtualRows` queue, and executes a custom Java `.sort()` utilizing `Comparable` interfaces mapped by the `sortInfoList`. If `DISTINCT` is requested, it generates a unique string hash of the entire row's projected output (`getRowKey()`) and uses a `HashSet` to ensure no duplicates are yielded.

## 7. Limitations and Production Challenges
While Boulder provides a powerful mechanism for virtualizing database states, applying it in a true Production testing environment introduces several architectural challenges and missing SQL capabilities:

*   **Missing SQL Features**:
    *   **Complex Aggregates & Grouping**: Features like `GROUP BY`, `HAVING`, and complex aggregate combinations are not fully virtualized.
    *   **Subqueries & CTEs**: Deeply nested subqueries, `EXISTS` clauses, and Common Table Expressions (CTEs) are difficult to parse and overlay with memory patches.
    *   **Window Functions**: Functions like `ROW_NUMBER()`, `RANK()`, or `OVER()` rely heavily on the DB engine and cannot be easily emulated in Java.
    *   **Advanced Data Types**: Native JSON operators, array aggregations, and spatial database queries are unsupported by the proxy.
    *   **String & Math Functions**: SQL functions used in `WHERE` clauses (e.g., `LOWER()`, `CONCAT()`, `MOD()`) cannot be reliably evaluated against in-memory patches without a full embedded SQL engine.
*   **Production Challenges**:
    *   **ThreadLocal & Concurrency Limits**: `ChalkBag` relies on `ThreadLocal`. In modern reactive, asynchronous (e.g., WebFlux), or coroutine-based frameworks where execution jumps across threads, the virtual state will be lost unless context-propagation is explicitly managed.
    *   **Memory Exhaustion (OOM)**: Operations like `ORDER BY` and `DISTINCT` force the proxy to drain the *entire* physical `ResultSet` into JVM memory to perform sorting and deduplication. Against production tables with millions of rows, this will cause `OutOfMemoryError`s.
    *   **Transaction Isolation desync**: If physical rows are modified by a separate real-user transaction during a virtual test, the physical baseline changes. Boulder's patches might then apply to mutated or deleted underlying data, leading to inconsistent test results.
    *   **Sequence/ID Collisions**: While Boulder starts generating IDs at 1,000,000, long-running production databases might eventually reach this sequence limit, causing virtual keys to collide with actual physical keys.
    *   **Performance Overhead**: `JSqlParser` is invoked on every single JDBC execution. In a high-throughput production environment, parsing the AST for every query introduces significant latency.

## Glossary

*   **Boulder**: The overarching JDBC proxy framework that intercepts and virtualizes database interactions.
*   **ChalkBag**: The thread-local, in-memory data store used to house all virtual inserts, updates (patches), and deletes (tombstones).
*   **DynoMerger**: The write-interception component responsible for parsing `INSERT`, `UPDATE`, and `DELETE` SQL commands and applying them exclusively to the `ChalkBag`.
*   **MergedResultSet**: The read-interception component that evaluates `SELECT` queries and algorithmically blends physical JDBC result sets with virtual `ChalkBag` state.
*   **Virtual Row**: A database row that exists either entirely or partially within the `ChalkBag` memory layer and is seamlessly injected into the application's read stream.
*   **Tombstone**: A `null` marker stored in the `ChalkBag` for a specific Primary Key, indicating to the proxy that the physical row has been "deleted" and should be hidden from all `SELECT` queries.
*   **Patch-to-Include (Pull-through)**: A proxy scenario where a physical row fails the underlying database's `WHERE` clause, but an in-memory update patch modifies the row such that it now *passes* the filter. The proxy must manually fetch and inject this row into the results.
*   **Patch-to-Exclude**: A proxy scenario where a physical row successfully passes the underlying database's `WHERE` clause, but an in-memory update patch modifies the row such that it now *fails* the filter. The proxy must actively hide this row from the results.
*   **Hybrid Row**: A constructed data record assembled by `MergedResultSet` that represents a physical base row overlaid with virtual memory patches. It often requires the proxy to issue targeted physical `SELECT` queries to complete missing data required by `JOIN` chains.
